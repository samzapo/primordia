# Revision 48 — persistent pond and account continuity

The owner explicitly authorizes three server introduction rules: keep at least fifteen living cells in the pond; give an exhausted account a new cell with a new lineage; archive and restart the pond if every living cell is gone. These supersede the earlier same-lineage-only recovery and no-reseed rules for the persistent service. Local single-player recovery remains unchanged.

Living descendants and existing prepaid dormant bodies remain the first recovery choice. Once neither exists, introduce a standard starter at a safe position and attach it to the same account. The access-key grant, session mapping, ordered command sequence and deduplication receipts remain intact; increment the edit version so a queued command cannot spend the replacement's resources using the old selection. Retain the previous eight lineage ledgers as account history. If the 64-body resident limit or safe placement prevents an introduction, retain the account and retry at most twice per simulation second. The UI shows that a new lineage is being prepared.

After each server tick, replenish a nonempty pond to fifteen living cells with independent unclaimed grazer lineages. These introductions carry the standard body's physical starter inventory; they never debit another cell or release an extra environmental food cloud. Reproduction remains a separate particle-funded transaction, with its existing four-member family and 64-body limits. No immigration path grants tissue or ATP to an existing body. Count introductions and account restarts separately in health telemetry. Empty geometry/capacity can temporarily delay placement; bounded retries remain necessary rather than overlapping bodies or exceeding GPU capacity.

An entirely empty pond takes precedence over individual account recovery or replenishment. Checkpoint it, close the resident GPU cleanly and exit with status 75; the existing persistent service supervisor restarts it. On startup, save an independent checksummed two-generation archive under `state/archives/pond-<world-id>--epoch-<epoch>--tick-<tick>/` before creating a new seeded population and world identity. Keep the epoch increasing, preserve every access-key/session mapping, and assign existing accounts to living founders in the new pond. Old bodies, time and command receipts remain in the archive. A failed archive prevents replacement. A corrupt checkpoint still fails closed. Healthy restarts resume the current pond without resetting it.

The deployment health gate permits an identity change only with an increasing epoch/restart count, the exact predecessor identity and a valid independently checksummed predecessor archive. Its normal same-world restart check remains. Deployment and restart retain the five-key registry outside world storage. Each reconnection refocuses the client camera after receiving its current account selection. Discard browser cell caches outside the current snapshot and reset interpolation caches on reconnect. Remove unused resident schedule IDs, exhausted unreferenced active ledgers and server-only legacy replacement queue entries so repeated introductions do not grow those caches indefinitely.

Gameplay/objective/balance tests remain held. Validation covers authentication continuity, stale edit isolation, explicit inventory sources, archive durability, checkpoint shared references, networking and actual resident GPU operation. No survival-rate or population-balance campaign is part of this revision.
